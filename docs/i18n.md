# Internationalisation

## Locales

| Code | Language | Direction |
| --- | --- | --- |
| `en-US` | English (US) — fallback | LTR |
| `pt-BR` | Português (Brasil) | LTR |
| `es-MX` | Español (México) | LTR |
| `fr-FR` | Français | LTR |
| `zh-CN` | 简体中文 | LTR |
| `hi-IN` | हिन्दी | LTR |
| `ar-SA` | العربية | **RTL** |

418 keys per locale are generated from `tools/locales-source.mjs`:

```bash
pnpm locales
```

Output: `locales/{locale}/common.json` + `locales/{locale}/modules/*.json`, plus a bundled English
fallback for the web app (`apps/web/src/i18n/fallback-messages.json`).

## Resolution order

1. User preference (`users.locale`)
2. Company default (`tenants.defaultLocale`)
3. Global default (`settings.default_locale`, editable in the UI; also persisted to `.env` when possible)
4. `en-US`

Guests use the `grc_locale` cookie (set by the language switcher) and then the global default.
`GET /api/i18n/messages` performs this resolution server-side and returns `{ locale, dir, messages }`.

## Backend contract

The API never returns translated UI copy:

- Errors: `messageKey` (`errors.validation`, `auth.invalidCredentials`, …) plus validation `issues`.
- Statuses: stored as stable keys (`under_review`, `not_applicable`) and translated by the client.
- Notifications: `titleKey` + `params` (`notification.riskCreated` with `{ title, score }`).
- Field metadata (`/api/:module/meta`) exposes field names; the client maps them to `fields.*`/`common.*`.

## RTL

`<html dir>` is set from the resolved locale. Layout uses logical CSS utilities (`ps-*`, `pe-*`, `ms-*`,
`me-*`, `start-*`, `end-*`) so Arabic mirrors automatically; the sidebar off-canvas transform is
direction aware. Charts and matrices keep numeric ordering.

## Overrides

Super Admin → Translations lists every key with its shipped value. Saving stores a row in `translations`
(`locale`, `namespace`, `key`, `value`); deleting the row restores the shipped value. Overrides are
merged over the JSON files on every `GET /api/i18n/messages`.
